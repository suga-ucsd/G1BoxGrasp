1. The problem ACT solves

Behaviour cloning is the simplest way to learn from demonstrations. Record what an expert sees and does, then train a network to map "what it sees" → "what it does". It's supervised learning, with the expert's action as the label.

It has one famous flaw: compounding error.

  • The network is never perfect, so each step it is slightly off.
  • Being slightly off puts the robot in a state the expert never visited, where the network is even less accurate.
  • The errors snowball. For naive behaviour cloning the expected error grows with the square of the number of decisions (Ross & Bagnell, 2010).

Fine manipulation makes this worse: a few millimetres of drift is the difference between threading a tie and missing it.

A second, subtler problem is that human demonstrations are not consistent. Two demos of the same moment can differ: the person paused, or went left of the object instead of right. A network trained with a plain regression loss averages those, and the average of "go left" and "go right" can be "go straight into the object". ACT's CVAE (section 4) is there for that.

2. Idea 1: action chunking

Instead of learning π(at | st), ACT learns π(at, at+1, …, at+k−1 | st): from one look at the world, the next k target joint positions.

  • In the original paper k = 100 at 50 Hz, i.e. 2 s of motion per prediction. Mobile ALOHA used k = 45; HumanPlus and ALOHA Unleashed used k = 50.
  • The simplest way to run it: predict a chunk, play all k actions open-loop, look again, predict the next chunk. LeRobot calls the number of actions played per prediction n_action_steps.
  • The catch: between predictions the robot is blind. If the box gets bumped halfway through a chunk, the robot won't react until the next one. Section 3 fixes this.

3. Idea 2: temporal ensembling

The fix: query the network every step anyway, and keep all the chunks. At any moment several chunks overlap, and each one has its own guess for "what to do right now". ACT plays a weighted average of those guesses:

at = Σi wi · at(i) / Σi wi, with wi = exp(−m · i)
  • i = 0 is the oldest chunk that still covers time t. With m > 0, the oldest prediction gets the largest weight. That sounds backwards, but it keeps the motion consistent: a fresh prediction nudges the plan rather than overriding it.
  • The paper and LeRobot use m = 0.01, a very gentle decay: a guess made 50 steps ago still has weight e−0.5 ≈ 0.61.
  • It costs nothing in training. At run time it means one network call per control step (10 ms per call on the paper's GPU), and in LeRobot it requires n_action_steps = 1.
  • It averages predictions for the same time step, so it isn't blurring motion over time like a low-pass filter. It removes the jumps at chunk boundaries.
Later work found a catchAveraging only makes sense if the guesses agree. When two chunks commit to different strategies (one goes left of the cup, one goes right), their average is a strategy nobody demonstrated.
  • Bidirectional Decoding (2024) found ensembling hurt 2 of 7 tasks, and that the best decay rate changes from task to task.
  • Real-Time Chunking (Physical Intelligence, 2025) saw it oscillate badly enough on a real robot to trigger the protective stop.
This is a bigger problem for multimodal policies (diffusion) than for ACT, whose test-time output is deterministic (section 4).

4. Idea 3: the CVAE ("style" variable)

Human demonstrations vary for reasons the camera can't see: the person hesitated, or picked another route. A regression network trained on them averages those choices and ends up hesitant or wrong. ACT gives the network a hidden variable z to put that variation into. That is the conditional variational autoencoder (CVAE).

  • Loss: L = L1(predicted chunk, true chunk) + β · KL(q(z) ‖ N(0, I)), with β = 10. The paper found L1 more precise than L2. LeRobot also uses L1, and masks out padded steps past the end of an episode.
  • What the KL weight does: with a large β, z carries little information and the policy has to rely on the observation. With a small β, the policy could lean on z to cheat during training, then fail at run time when z = 0.
  • When it matters: ACT's own ablation trained two simulated tasks with and without the CVAE.
    • On scripted demonstrations, which are perfectly consistent, it made almost no difference.
    • On human demonstrations, success fell from 35.3% to 2% without it.

5. The network, layer by layer

PieceWhat it does, in plain words
ResNet-18 per cameraTurns each image into a 15×20 grid of 512-number feature vectors, "what is in each patch". LeRobot starts it from ImageNet weights (ResNet18_Weights.IMAGENET1K_V1).
2D sinusoidal position codeTells the transformer where in the image each patch is, since attention by itself has no notion of position.
Transformer encoderMixes everything: every image patch from every camera, the joint state and z can all look at each other. This is where the "the box is here, my hand is there" reasoning lives.
Query tokens + decoderk learned vectors, one per future step. Each asks the encoded scene "what should I do at step j?" through cross-attention.
Linear headMaps each of the k answers to an action vector (14 numbers on ALOHA).

  • Data in the paper:

7. Running it on a robot

  • Two ways to play a chunk:
    • a queue: play n_action_steps actions, then predict again. Cheaper, but blind in between, with possible jumps at the boundaries.
    • temporal ensembling: predict every step and average. Smoother and more reactive, but one network call per step.
  • The actions are targets, not torques. A low-level controller tracks them: the motors' PD loop on ALOHA, an RL tracking policy on HumanPlus. The policy never has to learn balance or motor dynamics.
  • Latency: the network has to finish inside the control period. ACT takes about 10 ms, which fits 50 Hz. Big models (hundreds of ms) need asynchronous tricks such as real-time chunking (section 9).

9. What came after ACT

WorkWhat changedLesson for you
Mobile ALOHA (Fu, Zhao, Finn, 2024)ALOHA on a wheeled base. The action becomes 16 numbers: 14 arm joint targets + the base's linear and angular velocity. Three cameras, 50 demos per task, chunk 45. Co-training with 825 static ALOHA demos (50/50 sampling, base action set to 0 for static data) raised ACT from 0 → 95% on Call Elevator and 50 → 95% on Wipe Wine. A base-delay trick: play the first k−d arm actions with the last k−d base actions.Putting a velocity command for the base inside the action vector works, which is exactly what your 35-value action does with the walker command. Open-loop replay scored 0%, so closed loop is essential.
HumanPlus / HIT (Fu et al., 2024)A humanoid. A low-level RL policy (50 Hz) handles balance and tracks body targets. A decoder-only ACT variant (HIT) predicts chunks of 50 target poses at 25 Hz from two head cameras. It adds a loss that predicts future image features, so the policy can't ignore vision. Plain ACT got stuck on 2 of 6 tasks: 0% on typing and on wearing a shoe, against HIT's 80% and 60%.Closest to your setup: imitation on top of an RL walker. Watch for over-reliance on proprioception: ACT can learn "joint angles → next angles" and ignore the cameras.
ALOHA Unleashed (Zhao et al., 2024)The same group switched to a diffusion transformer, chunk 50, with 26,000+ demonstrations from 35 operators. On a messy shirt-hanging task: diffusion 70% against ACT 25%. On small simulated data, ACT was easier to tune and sometimes better.ACT is the right tool for tens to hundreds of consistent demos. Huge, varied human datasets favour diffusion or flow policies.
Bidirectional Decoding (Liu et al., 2024)Analyses the chunk-length trade-off. Long chunks help in deterministic settings; short chunks help when things are noisy or get disturbed. Ensembling and per-step resampling can average or flip between strategies. Their fix samples several chunks and picks the one consistent with the last chunk and closest to a strong model.Your scripted, deterministic expert is the case where long chunks are safe. If the policy dithers between two strategies, this is the known failure.
Real-Time Chunking (Black et al., 2025)For big, slow policies: compute the next chunk while the current one plays, with the actions that will run during the computation frozen ("inpainting"). This removes pauses and jumps. Temporal ensembling oscillated badly on their real robot.Only needed if inference becomes slow. ACT at about 10 ms doesn't need it.
Diffusion Policy (Chi et al., 2023)The main alternative. It generates the action chunk by iterative denoising, so it can represent several distinct ways of doing a task instead of averaging them. It's slower per call and also predicts chunks.The upgrade path if ACT averages away strategies your data needs.

10. Where ACT is weak

Known failure modes
  • One answer per situation. With z = 0 at test time, ACT outputs a single chunk. If the data contains two equally valid strategies, it may blend them. A consistent (scripted) expert avoids this.
  • Ignoring the cameras. If the joint angles alone predict the next actions well in training, the network can learn to rely on them and stop looking (HumanPlus). Varied starts and object positions force it to use vision.
  • Chunk length. Too short and it drifts and stutters; too long and it reacts late to bumps and slips (1% at k=1, 44% at k=100, worse again above).
  • Long, multi-stage tasks. The paper's episodes are 8–14 s. Very long tasks give the network more ways to lose track of which stage it is in.
  • Precision versus data. The paper's hardest task (thread velcro, 100 demos) reached only 20%. More, or more consistent, data is the main lever.
  • Validation loss is a weak guide. A low training loss doesn't mean a high success rate, so evaluate closed-loop.

11. What this means for the G1 box task

What the papers sayFor your data and training
CVAE matters for human data, not scripted dataYour demonstrations come from a deterministic script, so they're perfectly consistent. Keep the CVAE (it's cheap), but don't expect it to do much. Consistency is your advantage.
Long chunks are safe when things are deterministic (BID)Chunk 50–100 is fine for the reach, squeeze and walk. The catch and the moments a box is slipping are reactive, so prefer temporal ensembling (m = 0.01) for evaluation, which eval_act.py already does.
The paper's episodes are 8–14 sYours are about 40 s with six phases. Start the pilot with the catch-to-lift half (le2act.py --segment reach, about 12 s). Train the full task once that works, or keep two policies.
ACT can ignore vision (HumanPlus)Your expert reads the box position from the simulator, which the policy can't see. Randomize the box start, size and robot start enough that the cameras are needed. Check with a "frozen camera" test: if success doesn't drop, it isn't using vision.
50 demos per task worked at 8–14 sFor a 40 s, multi-box-size task, plan on a few hundred episodes (the pilot: 200 of one box), as the plan says.
Absolute joint targets beat deltasYour actions are absolute actuator targets. Keep it that way.
Base velocity in the action works (Mobile ALOHA)The walker command is in your action vector. Mind the walker's dead-band (it only steps above about 0.4–0.6 m/s): the policy has to learn bang-bang-like commands, which chunking reproduces well.
Evaluate closed-loopUse eval_act.py on the same seeds as the expert. Ignore validation loss for model selection.

12. Glossary and sources

TermMeaning
Behaviour cloning (BC)Supervised learning from demonstrations: observation in, the expert's action as the label.
Compounding errorSmall mistakes put the robot in unfamiliar states, where it makes bigger mistakes.
Action chunkThe next k actions predicted together from one observation.
Temporal ensemblingAveraging every overlapping chunk's prediction for the current step, weighted exp(−m·i) from the oldest.
CVAEConditional variational autoencoder: a latent z captures the variation the observation can't explain; z = 0 at test time.
KL weight βHow strongly z is pulled towards a standard Gaussian (10 in ACT).
Query tokensLearned vectors that ask the transformer for one output each (DETR's object queries, ACT's future steps).
ProprioceptionThe robot's own state: joint positions, IMU.
Co-trainingTraining on a mix of the task data and related data, sampled together each batch.
