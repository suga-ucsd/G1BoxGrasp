data_pipeline: how the code works

Code guide for G1BoxGrasp/data_pipeline/, the Python half of the ACT data pipeline planned in plans/G1_ACT_data_pipeline_plan.html. 28 October 2026; updated 30 October for LuckyEngine 2026.1.2 (MujocoFull recorder) after the first real sessions. Written against lerobot 0.6.1 and luckyrobots 0.5.0, and checked against their source.
In short

Six files take a recorded LuckyEngine session to a trained and evaluated ACT policy:

  1. qa.py checks each recorded session.
  2. inspect_session.py renders it as an HTML page of checks, camera frames and charts.
  3. le2act.py converts sessions and their script sidecars into a LeRobot 3.0 dataset.
  4. train_act.sh trains ACT on it.
  5. eval_act.py runs the trained policy closed-loop in the engine over gRPC.

common.py holds everything they share: the vector layouts, the column names and the readers. make_fake_session.py writes a synthetic session, so the whole chain can be tested without the engine. Section 9 has the test that was run.

The C# side Two C# pieces from the plan live with the controller in src/, and these scripts depend on their output.
  • The episode runner (src/Recording/Episodes.cs, inspector group Recording) records each run as one Observer episode, resets the scene between episodes and writes the sidecar described in section 3.3. Working in the engine since 30 October 2026 (section 9.2). No randomization yet: every episode after a reset is identical.
  • G1ActAgent.cs publishes and accepts the vectors described in section 8. Not written yet.
make_fake_session.py stands in for the recording side in the self-test.

2. The vectors: state, action, status

These are defined once in common.py. Every script and both C# pieces use the same order.

VectorSizeContents, in order
observation.state37
  • qpos of the 31 upper-body joints:
    • 14 arm joints: left then right, each shoulder pitch, roll, yaw, elbow, wrist roll, pitch, yaw;
    • 14 hand joints: left then right, each thumb 0/1/2, index 0/1, middle 0/1;
    • 3 waist joints: yaw, roll, pitch.
  • The pelvis IMU, worked out from the recorded pelvis orientation (MujocoFull records no sensors): gravity in the pelvis frame (x, y, z) and the pelvis angular velocity (x, y, z, rad/s, from consecutive orientations). A real G1's pelvis IMU gives both.
Names are q.<joint>, imu.pelvis_gravity.x, …, imu.pelvis_gyro.z.
action35
  • The 31 upper-body actuator commands, same joint order. Names are u.<joint>.
  • Then waist_lock (0/1) and the walker command cmd_vx, cmd_vy, cmd_yaw.
phase1The phase index:
  1. catch
  2. grasp
  3. lift
  4. carry
  5. place
  6. retract
It's stored in the dataset but isn't a policy input: LeRobot only feeds keys that start with observation. to the policy.
agent status3Appended to the state by G1ActAgent during evaluation only: done, success, phase.

3. Inputs: session, sidecar

3.1 Observer session (MujocoFull recorder mode, LuckyEngine 2026.1.2)

session_<date>_<time>/
  data/chunk-NNN/file-NNN.parquet         one row per robot per data tick
  meta/info.json, meta/episodes/chunk-NNN/file-NNN.parquet
  videos/observation.images.<OutputName>/chunk-NNN/file-NNN.mp4   one file per episode

Sessions are written to <project>/DataSessions/session_<date>_<time>/. This engine version's recorder has three data modes (RobotArm, MujocoFull, Drone) and no Custom Schema; MujocoFull is used. Each row holds index, sim_id, timestamp, episode_index, frame_index, task_index, frame_flags and two vectors, both named in meta/info.json:

ColumnContentsUse
observation.state (57)The whole qpos: the pelvis free joint (floating_base_joint_x … _qz), all 43 joints, the box free joint (PoolBox_01_x … _qz).q.<joint>; pose.pelvis and pose.box.<Tag> (privileged, analysis only); the pelvis IMU.
action (43)Every actuator's ctrl, by joint name. The walker drives the legs and waist through its own channel, so those record as 0; the script-written arm, hand and (locked) waist ctrl are exact.u.<joint>: the first 31 actions; u.left_wrist_roll_joint is the alignment probe.
frame_flagsBits new_policy_step, post_reset.flag.post_reset: a reset may only appear on frame 0.

read_session expands these into the named columns above, so the other scripts never see the raw vectors. Videos are videos/observation.images.head_camera/chunk-NNN/file-NNN.mp4, one per episode, 256×256, located through meta/episodes. StopRecording appends an empty (length 0) episode row there, which the reader skips.

3.3 Sidecar (written by the C# episode runner)

The Observer can't record values that exist only in the script. So the episode runner writes two files per episode into its own folder (for example DataSidecars/run_<time>/). Their numbering follows the Observer's episode order, from 0.

FileContents
episode_NNNNNN.csvOne row per control tick (50 Hz), written in OnUpdate:
  • frame and sim_time;
  • task_index, the phase;
  • waist_lock;
  • cmd_vx, cmd_vy, cmd_yaw: the intended walker command;
  • probe_ctrl: the value the script wrote to the left wrist-roll actuator this tick;
  • optionally exec_vx, exec_vy, exec_yaw: the command actually sent, when walker noise was injected.
episode_NNNNNN.jsonHeader:
  • episode, seed;
  • success, fail_reason;
  • box {tag, width, depth, height, mass};
  • box_start, robot_start, perturbation;
  • release_error {height, planar};
  • max_slip, max_wrist_dev_deg.
The success value here takes precedence over the Observer's.

4. common.py

  • Layouts. UPPER_JOINTS (31) is built from the side, arm and hand name parts, so the order never depends on the MJCF's actuator order. The MJCF lists the right hand as thumb, index, middle and the left as thumb, middle, index. STATE_COLUMNS are the expanded session column names; STATE_NAMES are the 37 state names. ACTION_NAMES adds the four sidecar values.
  • read_session(root, entity=None)
    • Reads every data Parquet file, expands the MujocoFull vectors (expand_mujoco_full) and keeps one robot: the most frequent sim_id, or the one given.
    • Groups the rows by episode_index, sorted by frame_index.
    • Adds the pelvis IMU columns per episode (pelvis_imu).
    • Attaches each episode's video path and start timestamp per stream, plus its meta/episodes row.
    Returns (info, [Episode]).
  • read_sidecar(root, index) reads episode_NNNNNN.json and .csv into a Sidecar(header, rows), or None if the CSV is missing.
  • matrix(rows, columns) returns a (T, n) float array. Scalar columns add one value each; list-valued columns add their width, so a 3-wide IMU column adds 3.
  • action_shift(rows, side) finds which Observer row holds the ctrl of control tick k. For shift s = 0, 1, 2 it compares the recorded probe ctrl at row k+s with the probe_ctrl the script wrote at tick k, and returns the shift with the smallest mean error and that error.
    • The probe is a script-owned actuator (a wrist), because its ctrl is known at OnUpdate time. The IK-owned shoulders are written later in the same step.
    • The Observer captures before control, so the expected answer is 1, but the code measures it rather than assuming it.
  • episode_arrays(ep, side, shift) builds one episode's arrays: state from row k, the 31 ctrl values from row k+shift, and the waist lock, walker command and phase from sidecar tick k. Its length is the shorter of the two sources, minus the shift.
  • segment(phase, which) picks the frames for one half of the two-policy option: reach is catch to lift, up to the first carry frame; carry is from there to the end; all is everything.
  • mjcf_ranges(path) reads joint ranges from the MJCF. The position actuators use inheritrange="1", so these are their control ranges.
  • pelvis_imu(pose, fps) turns the pelvis pose rows into gravity in the pelvis frame (RT·(0, 0, −1)) and the body-frame angular velocity 2·fps·vec(qk−1* qk), 0 on the first row.

5. inspect_session.py

One self-contained HTML page per session, to judge the data by eye before converting. Per episode:

  • Checks, each pass, warning or fail: missing values, frame counter gaps, tick spacing, resets inside the episode, commands outside the joint ranges, one video frame per row, frozen frames (a live render never changes by under 0.02 per pixel), black frames, sidecar length, action alignment (the probe error at shifts 0, 1 and 2, and whether the probe moves enough to pin the shift down), waist lock values, phases present and in order, and the expert's outcome.
  • The phase timeline and each camera's frame at every phase start and at the end.
  • Charts (hover for values): every joint's measured angle against its command, lined up by the found shift; the walker command; the waist lock; the pelvis IMU; the box height and distance from the pelvis; the pelvis path.

The page's verdict is the worst check of any episode; episodes that disagree on the action shift fail the session.

6. qa.py

Run once per session, before converting. Hard errors (exit code 1):

  • NaN in the state or ctrl columns; frame_index not running 0, 1, 2, …
  • A camera's video missing, or its frame count different from the episode's row count (frames are counted by decoding).
  • flag.post_reset set on any frame but 0: a reset leaked into the episode.
  • A ctrl value outside its joint's range (from the MJCF).
  • No sidecar, or a sidecar more than 2 ticks longer or shorter than the episode.
  • Alignment unclear: even the best shift leaves a probe mismatch over --max-shift-err (1e-4). Episodes disagreeing on the shift is also an error.
  • waist_lock not 0 or 1.

The summary table prints, and with --csv it's also saved. Per episode it has:

  • frames, success, the shift and the seed;
  • box width and mass, and the perturbation;
  • the largest sink, the largest wrist deviation and the release error;
  • seconds per phase.

After the table come the success count, the shifts found, the mean time per phase, and text histograms of box width and mass, to check the randomization covers what was asked for.

7. le2act.py

  1. Pairs each --session with its --sidecar, in the order given. Reads one session at a time, so memory stays bounded by the biggest session, not by the whole dataset.
  2. Per episode, it skips the episode, giving the reason, if:
    • the sidecar is missing;
    • one of the cameras has no video;
    • it failed (unless --include-failures);
    • the chosen --segment is empty.
    Otherwise it finds the action shift (--shift auto, or a fixed number), builds the arrays, and trims them to the shortest video.
  3. Writes through LeRobot. LeRobotDataset.create(repo_id, fps, features, root, robot_type, use_videos=True) on the first kept episode. Then add_frame per frame and save_episode per episode, and finalize() at the end. Without that last call the Parquet footers aren't written and the dataset is invalid.
    • Each frame dict holds the state, the action, the phase, one RGB array per camera, and "task".
    • LeRobot adds timestamp and frame_index itself.
    • The features are float32 for state and action, int64 for the phase, and video (H, W, 3) per camera.
  4. Video. video_frames decodes each episode's MP4 with PyAV, from the episode start (plus the segment's offset), resizing to --size as it decodes. The three cameras are read in lockstep, one frame each per data row, so only one frame per camera is ever held in memory. LeRobot re-encodes them into its own video files.
  5. Report. Prints one line per episode, writes conversion_report.json (kept episodes with source, shift, seed and box; skipped episodes with the reason) next to the dataset. --dry-run does all the checks and writes nothing.
Why the walker command comes from the sidecar, and as the intended value For walker noise (DART), the sidecar logs both the intended command (cmd_*) and the executed one (exec_*). The dataset takes the intended command, so the policy learns the expert's correction rather than the noise. The 31 joint commands, though, are the executed ctrl the engine recorded. So noise must never be injected into the arm targets. Use small pushes on the box or the hands instead: the labels stay clean, and the data still contains the recoveries.

8. train_act.sh and eval_act.py

8.1 train_act.sh

One lerobot-train call in three modes:

ModeStepsBatchUse
smoke202On the CPU: checks the dataset loads and the policy trains.
pilot30k8The catch→lift pilot (M3).
full100k8The whole task (M4).

ACT settings:

  • chunk_size=50 and n_action_steps=50: 1 s at 50 Hz.
  • kl_weight=10, optimizer_lr=1e-5: the paper's defaults.
  • push_to_hub=false: it defaults to true in lerobot 0.6.
  • wandb off.

Output goes to outputs/act_g1_<mode>_<dataset>/.

8.2 eval_act.py

  1. Policy. Loads the checkpoint's config. Unless --ensemble 0, it turns on temporal ensembling (coefficient 0.01, n_action_steps=1): a chunk is predicted every step and the overlapping chunks are blended. That smooths the arms while they hold the box. Then it loads ACTPolicy.from_pretrained(path, config=cfg) and the saved pre- and post-processors (make_pre_post_processors(cfg, pretrained_path)), which hold the normalization statistics.
  2. Engine. Session(host, port).connect(robot=...) attaches to the running editor's gRPC server; nothing is launched. configure_cameras asks for the three cameras at the training size, so frames arrive already resized.
  3. Loop, per episode.
    1. policy.reset(), then session.reset().
    2. Each step:
      • split the agent's observation into the 37 state values and the 3 status values;
      • stop on done;
      • turn each camera frame (RGBA bytes) into HWC RGB;
      • prepare_observation_for_inference (to tensors, images to [0,1] CHW, batch dimension), then the pre-processor, select_action and the post-processor;
      • session.step(action).
    The External Action Gate advances exactly one tick per step, so there's no sleeping or wall-clock pacing.
  4. Results. Per episode: success, done, steps, the furthest phase reached and the wall time, written to --csv. Progress shows in the editor's gRPC panel through report_progress. It fails fast, with a message, if the agent's vector sizes or the camera names don't match.
Contract for G1ActAgent.cs (to write)
  • OnState publishes the 37 state values in the order of section 2, followed by done, success and phase.
  • OnAction takes the 35 actions:
    • the first 31 go to the upper-body actuators;
    • the waist values are applied only when waist_lock > 0.5; otherwise the walker keeps the waist;
    • the last three go to the walker slot as (vx, vy, yaw rate).
  • Resets draw from the same seeded parameters as the recording runner, so the agent's episodes can be paired with the expert's.

10. Design decisions and limits

  • Joint-space actions plus the walker command. These are exactly what the expert executes. No IK at deployment, and the legs stay with the RL walker.
  • MujocoFull, not Robot Arm mode. Raw ctrl by name (Robot Arm mode rescales it) and the full qpos, with the privileged poses kept apart from the policy inputs. LeRobot's action and observation.state are built by the converter. The IMU is derived from the pelvis orientation because this mode records no sensors.
  • Writing through the LeRobot API rather than patching the Observer's files in place. It re-encodes the videos, which is slower, but the output is whatever lerobot-train expects, and dropping failed episodes doesn't need episode metadata rewritten by hand.
  • Measured alignment. The shift between a control tick and its recorded ctrl comes from a probe actuator, per episode, and QA flags any disagreement.
  • Still open: camera frame t and data row t are paired by index (the counts match exactly, but no visible event has been timed against a row); and whether the engine's evaluation frames match the 256×256 training frames.
