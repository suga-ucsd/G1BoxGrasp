G1 box task: a data collection pipeline for ACT

Plan, 27 October 2026 · turns the scripted controller g1_grasp.cs (catch → grip → carry → place) into an expert that records LeRobot 3.0 datasets in LuckyEngine, then trains and evaluates an ACT policy on them · companion to report/G1BoxGrasp_report.html · repo ~/projects/robot_code/G1BoxGrasp
In short

The scripted controller already solves the task from privileged state: the box pose from MuJoCo and tared contact forces. This plan uses it as a demonstrator. Every episode is recorded by the engine's Observer as a LeRobot 3.0 dataset: head and wrist camera video plus joint positions and actuator commands, at the control rate.

The script adds the values the engine can't record: the walker's velocity command, the waist lock, phase labels and the episode's randomized parameters. A converter joins these into one ACT-ready dataset. ACT then learns to replace g1_grasp.cs: it maps images and proprioception to chunks of arm, hand and waist targets plus a walker command. The trained RL walker keeps the legs balanced, as it does now.

Evaluation runs closed-loop in LuckyEngine over gRPC, on the same seeds as the expert, so every policy failure can be compared with what the expert did.

Prerequisite Finish the size and weight test plan first (report, section 18). An expert that drops 10% of its boxes produces 10% unusable episodes and teaches a policy its failure modes. Target: at least 90% expert success across the whole distribution of boxes the dataset will cover. The two known open failures need fixing before any recording: the 0.1 m box slipping as Place begins, and the 2 kg box sinking 4.4 cm.

2.3 Actions

ChannelSizeSource when recording
Arm joint targets14The actuator ctrl written by the LimbIK (shoulders, elbow) and the wrist servo or latch (wrists).
Hand joint targets14Actuator ctrl: the script's curl and thumb commands (unused joints stay constant).
Waist targets3Actuator ctrl: the walker's own output while unlocked, the held angles while locked.
Waist lock1Script sidecar: 1 from grip confirm to Place, 0 otherwise. At deployment, above 0.5 means the agent drives the waist; below it, the walker does.
Walker command3Script sidecar: (vx, vy, yaw rate) exactly as sent to the walker slot.

That gives 35 action values at the control rate. Joint space is ACT's native action space, so no IK is needed at deployment, and the policy learns the arm postures the IK produced, including the elbows-out pole. The walker command is low-dimensional, and the expert's discrete pattern of "stop, wait for the box, turn, walk" is exactly what action chunking reproduces well.

3. What the engine records, and what it can't

  • Observer sessions. Hazel.Data.Observer: StartRecording, BeginEpisode, EndCurrentEpisode(success), StopRecording, RegisterTask / SetCurrentTaskIndex. Each session is one DataSessions/session_<date>_<time>/ folder in LeRobot 3.0 layout: data/chunk-NNN/file-NNN.parquet, one MP4 per camera per episode, and meta/ with info.json, stats.json, tasks and an episodes table that includes success.
  • Recorder mode: Custom Schema. One named column per quantity, declared in a YAML file: mujoco.qpos, qvel, ctrl, sensor, body_pose and engine.*. It records the 35 action channels' ctrl raw (not rescaled as in Robot Arm mode). It also records the IMU sensors, and the privileged box and pelvis poses as separate columns that the converter can leave out of observation.state. The Appendix has a sketch of the schema.
  • Rates. Record data and cameras on the 50 Hz Robot runner, so every control step has a row and a frame. If three cameras at 50 Hz drag the simulation far below real time, drop all streams together to 25 Hz; one uniform rate matters more than a high one.
  • Frame flags. post_reset marks the first frame after ResetToInitialState. The converter uses it to check that no reset leaks into an episode.
  • What it can't record. There is no C# or gRPC call that adds columns. The Custom Schema only reads MuJoCo and engine values, so the walker command, the waist lock flag, the phase and the episode parameters live only in the script. Fix: a sidecar. The episode runner writes one CSV per episode (or one Parquet per session) next to the session folder, one row per control tick:
    • episode index and frame index, the same counters as the Observer;
    • sim time;
    • walker command;
    • waist lock;
    • phase;
    • the IK targets, as an auxiliary signal.
    The episode header holds the seed and the randomized parameters. The converter joins on (episode, frame).
  • Alignment verify. The Observer captures in the Acquisition stage, before OnUpdate. So row k holds the state before the script's control at step k, and its ctrl column holds the command from step k−1. The converter must pair statek with the command the script issued at step k: sidecar row k, or ctrl of Observer row k+1. Check this on a 10-episode test session by comparing the two sources.
  • Quota. Recording needs a LuckyHub sign-in and counts against the account's monthly episode quota. Check the quota before planning 1,000-episode sessions.
  • Sync points. Leave them off for training data: the docs recommend keeping the natural recorder phase jitter for robustness. Use them only for a fixed regression session, where episodes must be bit-identical.

4. Expert changes: the episode loop

A new, small episode runner wraps the existing phase machine. It goes in a partial class file, so the controller logic is untouched.

  1. Session start. Register the task labels (below), then StartRecording(). Put RecordEpisodes and EpisodeCount in the inspector. Off by default.
  2. Episode start.
    1. Draw the episode parameters from a seeded RNG (section 5) and log the seed.
    2. Place the box and the robot.
    3. Let the body settle, then BeginEpisode().
    4. Release the box down the belt.
  3. Phase labels. Call SetCurrentTaskIndex on every Advance():
    • 0 catch;
    • 1 grasp (PreGrasp, Squeeze);
    • 2 lift (Lift, PullIn);
    • 3 carry (BackOff, TurnToTable, WalkToTable, FaceTable);
    • 4 place (Place, Release);
    • 5 retract.
    They cost nothing, and they let the converter cut segments for option C.
  4. Episode end. EndCurrentEpisode(success) when Retract finishes, on any Fail(), or on a cycle watchdog (90 s). Success means:
    • the box was released within 2.5 cm above its slot and 3 cm of it in the plane;
    • the box is still there 1 s after release;
    • no drop.
  5. Reset, between episodes so it isn't recorded.
    1. ResetToInitialState().
    2. A full C# state reset: phase, timers, the grip (gap, curl, held), the waist lock released, the walker re-armed with zero commands for a few ticks, the IK re-snapped to the live palms, and the pole and carry frame reset.
    3. The first frame after the next BeginEpisode must carry post_reset.
  6. Parked placed boxes. Since the table fills up, either clear it on reset (the box pool goes back to its parking spots), or rotate through the slots and clear only when they're all full.
Keep the expert's decisions recordable Every decision the expert makes from privileged information has to be visible in the observations, or the policy can't imitate it:
  • when to start the catch: the box is on camera;
  • when the grip counts as confirmed: palm contact shows on the wrist cameras, and in the touch channel if it's added;
  • when the box has stopped swinging: the IMU and the cameras.
Waits that end on a privileged threshold are fine. ACT learns them as "pause until this looks right".

5.1 Recovery data

Behaviour cloning only sees the states the expert visits. Once the policy drifts off them, it has no examples to recover from. Two cheap remedies:

  • Noise injection (DART). In 30–50% of episodes, perturb the executed walker command by ±0.05, as low-pass noise, and keep the expert's intended command as the label. The expert is closed-loop, so it corrects the drift, and the dataset then contains those corrections. The sidecar records both values. Don't add noise to the arm targets: their labels are the executed actuator commands the engine records, so the noise would end up in the labels. For the arms, use small pushes on the hands (applied forces) instead, which leave the labels clean.
  • Disturbance episodes. In 10–20% of episodes, apply a short push to the box through SetQfrcAppliedByDof during the carry, or delay the catch by a random 0–0.3 s. These record the expert's slip boost, re-squeeze and re-centring.

Label these episodes in the sidecar header, so training can mix or exclude them.

6. Converter and dataset checks

data_pipeline/le2act.py (Python 3.12, pandas or pyarrow, lerobot 0.6):

  1. Read meta/episodes/, the data Parquet files and the sidecar, and join them on (episode_index, frame_index).
  2. Build observation.state (the 37 proprioception values, plus 2 touch if recorded) and action (35), with the alignment fixed by the check in section 3.
  3. Rename the camera streams to observation.images.head, .wrist_left and .wrist_right.
  4. Keep the successful episodes. Write the failures to a separate split for analysis.
  5. Recompute stats.json over the kept episodes. Write a LeRobot 3.0 dataset that lerobot-train loads unchanged.

data_pipeline/qa.py, run on every session before training:

  • Integrity: no NaNs, and the frame count per episode equals the video frame count for every camera.
  • post_reset appears only on frame 0.
  • Every action is inside its actuator's control range; the waist lock is 0 or 1.
  • The alignment check above holds, to the last bit.
  • Per episode: success, length, time per phase, the largest box sink, the catch impact and the wrist deviation (the same numbers as the test plan's log summariser).
  • A histogram of the randomized parameters, to show the coverage is what was asked for.
  • Ten random episodes viewed in the LeRobot dataset viewer (Rerun), side by side with their GR logs.

7. Training ACT

SettingStart withWhy
Policy--policy.type=actLeRobot's ACT: a ResNet-18 backbone per camera, a transformer encoder and decoder, and a CVAE latent.
Chunk size / actions executed50 / 50 (1 s at 50 Hz)About the length of the expert's slowest single motions (the turn ramp, the squeeze). Try 100 if motions look jerky between chunks.
Temporal ensemblingOn at evaluation, coefficient 0.01Smooths the overlapping chunks. The arms must not jolt a held box.
Images3 × 240×320Ablate the wrist cameras: head only, against head plus wrists.
KL weight, learning rate, batch10, 1e-5, 8–16ACT paper defaults.
Steps100k (pilot 30k)Watch the closed-loop success, not the loss: ACT's validation loss barely tracks it.
DataPilot 200 episodes of one box; then 500–1,000 across the randomizationA 40 s episode is about 2,000 frames at 50 Hz, so 500 episodes is about a million frames.

Long horizon. At about 40 s and six phases, this is longer than the usual ACT tasks (10–20 s). If one policy loses track of the phase (for example, it reaches again while carrying), switch to option C. Train two policies on the phase-label segments: catch→lift and carry→place. Switch between them on the grip-confirmed event, which a small classifier on the wrist cameras can detect, or simply on time.

8. Closed-loop evaluation in LuckyEngine

  • Engine side. A G1ActAgent : RobotAgent, registered through a RobotManager in the scene.
    • Its JointSpec covers the 31 arm, hand and waist actuators only.
    • OnAction writes their targets, and passes the walker command and the waist lock to the existing walker plumbing (Drive and HoldWaist). The legs stay with the walker slot.
    • OnState publishes the same 37 proprioception values as the dataset, followed by done, success and phase.
    • The episode runner resets the scene with the same seeded parameters as the expert's episodes.
  • Python side. The luckyrobots Session:
    1. start, then configure_cameras with the three cameras at the training resolution.
    2. reset, then a settle.
    3. step(action) until success or a timeout.
    The External Action Gate holds the simulation in lock-step, one tick per step. Pace the loop by step count, never by the wall clock. Frames come back as RGBA, so slice them to RGB.
  • Paired evaluation. Run N seeds, with the expert and ACT on the same seeds. Report:
    • success per (width, mass) bucket;
    • the phase reached;
    • the drop rate;
    • placement error;
    • time, against the expert's.
    A seed the expert passes but ACT fails is a policy failure, and its video plus state trace decides the next data to record.
  • Iterate. Add targeted episodes, more randomization or more recovery data, and retrain. A DAgger-style relabelling would need the expert to act from any state. That needs a phase estimator for g1_grasp.cs, so it's a later step.

Appendix. Column schema sketch

Names must match the MJCF exactly; every actuator is named after its joint. One entry per joint is shown for each group; the full file lists all of them.

version: 1
columns:
  # proprioception (observation.state)
  - { name: q_left_shoulder_pitch,  source: mujoco.qpos, select: { joint: left_shoulder_pitch_joint } }
  #   ... 14 arm, 14 hand (left/right_hand_thumb_0..2, index_0..1, middle_0..1), 3 waist
  - { name: q_waist_yaw,            source: mujoco.qpos, select: { joint: waist_yaw_joint } }
  - { name: imu_torso_gyro,         source: mujoco.sensor, select: { sensor: imu-torso-angular-velocity } }
  - { name: imu_torso_acc,          source: mujoco.sensor, select: { sensor: imu-torso-linear-acceleration } }
  # actions (ctrl of the 31 upper-body actuators; the walker command comes from the sidecar)
  - { name: u_left_shoulder_pitch,  source: mujoco.ctrl, select: { actuator: left_shoulder_pitch_joint } }
  #   ... same 31 actuators
  # privileged, for analysis and success labels only (never policy input)
  - { name: pelvis_pose,            source: mujoco.body_pose, select: { body: pelvis } }
  - { name: box_pose,               source: mujoco.body_pose, select: { body: lucky_body_<box entity id> } }
  - { name: reset_flag,             source: engine.frame_flag, select: { flag: PostReset } }

The box body names are lucky_body_<entity id> (one per pool box). Read the IDs from the scene's .hscene.auto. A schema that names a missing joint, actuator, sensor or body refuses the recording, and the Log panel says why.
